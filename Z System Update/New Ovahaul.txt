
# Database Tables Summary

## 1. roles — User Roles & Permissions
**Purpose:** Defines different user types and their system permissions

**Key Fields:**
- `role_id` (PK) — Unique identifier
- `role_name` — Administrator, Supervisor, Cashier, Lecturer, Student
- `role_level` — Permission hierarchy (1–5)
- `can_manage_users`, `can_process_payments`, etc. — Granular permissions

**Relationships:**
- 1:M with `users` (One role → Many users)

---

## 2. programmes — Academic Programmes
**Purpose:** Stores academic programmes offered by the department

**Key Fields:**
- `programme_id` (PK)
- `programme_code` — e.g., "BTECH-ICT"
- `programme_name` — e.g., "BTech Information Communication Technology"
- `programme_type` — BTech, HND, Diploma, Certificate

**Relationships:**
- 1:M with `students` (One programme → Many students)
- 1:M with `dues` (Programme-specific dues, nullable)

---

## 3. academic_sessions — Academic Years
**Purpose:** Defines academic sessions/years

**Key Fields:**
- `session_id` (PK)
- `session_name` — e.g., "2024-2025"
- `start_date`, `end_date`
- `is_current` — Flags current active session

**Relationships:**
- Indirect through `payments.academic_year` and `dues.academic_year`

---

## 4. users — System Users
**Purpose:** Authentication and user profiles for ALL system users

**Key Fields:**
- `user_id` (PK)
- `username`, `password_hash` — Login credentials
- `email`, `phone`, `first_name`, `last_name`
- `role_id` (FK → `roles`) — User's role
- `is_active` — Account status

**Relationships:**
- M:1 with `roles` (Many users → One role)
- 1:1 with `students` (One user → One student, optional)
- 1:M with `payments` as `created_by`/`verified_by`
- 1:M with `dues` as `created_by`
- Self-referencing (`created_by` → `users.user_id`)

---

## 5. students — Student Information
**Purpose:** Core student demographic and academic data

**Key Fields:**
- `student_id` (PK)
- `index_no` — Unique student index number
- `first_name`, `last_name`, `email`, `phone`
- `programme_id` (FK → `programmes`)
- `programme_level` — 100, 200, 300, 400
- `current_academic_year`
- `status` — Active, Inactive, Graduated, etc.
- `user_id` (FK → `users`, nullable) — Login account link

**Relationships:**
- M:1 with `programmes` (Many students → One programme)
- 1:1 with `users` (Optional student login account)
- 1:M with `payments` (One student → Many payments)

---

## 6. dues — Dues/Fees Configuration
**Purpose:** Configurable dues amounts for different academic years/programmes

**Key Fields:**
- `due_id` (PK)
- `due_name` — e.g., "Departmental Dues 2024-2025"
- `due_code` — Unique code: "DEPT-2024-2025"
- `amount` — Required payment amount
- `academic_year` — Which year this applies to
- `programme_id` (FK → `programmes`, nullable) — Programme-specific or all
- `created_by` (FK → `users`)

**Relationships:**
- M:1 with `programmes` (Optional: dues can be programme-specific)
- M:1 with `users` (Who created this due)
- 1:M with `payment_items` (One due → Many payment line items)

---

## 7. payments — Payment Transactions
**Purpose:** Records all payment transactions

**Key Fields:**
- `payment_id` (PK)
- `receipt_no` — Unique receipt number
- `student_id` (FK → `students`) — Who paid
- `academic_year` — Which academic year being paid for
- `amount_paid`, `total_amount`, `balance`
- `payment_date`, `payment_method`, `payment_status`
- `created_by` (FK → `users`) — Who processed payment
- `verified_by` (FK → `users`, nullable) — Who verified payment

**Relationships:**
- M:1 with `students` (Many payments → One student)
- M:1 with `users` as `created_by` and `verified_by`
- 1:M with `payment_items` (One payment → Many line items)

---

## 8. payment_items — Payment Line Items
**Purpose:** Breakdown of what dues were paid in each transaction

**Key Fields:**
- `payment_item_id` (PK)
- `payment_id` (FK → `payments`) — Parent payment
- `due_id` (FK → `dues`) — Which due was paid
- `amount` — Amount paid for this specific due
- `academic_year` — Academic year for this due

**Relationships:**
- M:1 with `payments` (Many items → One payment, CASCADE delete)
- M:1 with `dues` (Many items → One due type)

---

## 9. student_academic_years — Payment Progression Tracking
**Purpose:** Tracks which academic years each student has paid for

**Key Fields:**
- `student_year_id` (PK)
- `student_id` (FK → `students`)
- `academic_year`
- `is_paid` — Boolean for payment completion
- `total_paid` — Sum for this year
- `payment_completed_date`

**Relationships:**
- M:1 with `students` (Many year records → One student)

**Constraints:**
- Unique constraint: One record per student per academic year

---

## 10. audit_logs — System Audit Trail
**Purpose:** Logs all important system changes for security/compliance

**Key Fields:**
- `audit_id` (PK)
- `table_name` — Which table was modified
- `record_id` — Which record was modified
- `action` — INSERT, UPDATE, DELETE, LOGIN, etc.
- `old_values`, `new_values` — JSON data changes
- `changed_by` (FK → `users`, nullable) — Who made change

**Relationships:**
- M:1 with `users` (Many logs → One user who made change)

---

## 11. configurations — System Settings
**Purpose:** Stores application configuration settings

**Key Fields:**
- `config_id` (PK)
- `config_key` — Setting name/key
- `config_value` — Setting value
- `config_type` — string, integer, boolean, json
- `is_public` — Whether setting is publicly accessible

**Relationships:**
- Independent table (no foreign keys)


## Key Design Principles:
**Normalization:** Minimal data redundancy
- **Referential Integrity:** Foreign keys with constraints
- **Audit Trail:** Complete change history
- **Soft Deletes:** Data preservation
- **Flexibility:** Programme/year-specific configurations
- **Security:** Role-based access control at database level


# CSV Import Data Validation & Auto-Population Guide

## Data That Can Be Safely Auto-Populated:

### 1. Auto-Generated Unique Identifiers
-- System can generate if missing:
- receipt_no (for payments): Using stored procedure GenerateReceiptNumber()
- user_id (for users): Auto-increment
- student_id: Auto-increment
- payment_id: Auto-increment

### 2. Timestamps (Always Auto-Populated)
-- These should NEVER come from CSV, always system-generated:
- created_at (current timestamp)
- updated_at (current timestamp)
- last_login (NULL initially)
- payment_date (if missing, use current date for payments)

### 3. Default Status Values
-- If CSV missing these, use defaults:
- students.status = 'Active' (if missing or invalid)
- payments.payment_status = 'Completed' (if payment amount > 0)
- users.is_active = TRUE
- dues.status = 'Active'
- users.must_change_password = TRUE (for new accounts)

### 4. Calculated/Inferred Fields
-- Can be calculated from existing data:
- payments.balance = total_amount - amount_paid
- student_academic_years.is_paid = TRUE (if payment exists)
- student_academic_years.total_paid = SUM of payments for that year

## Data That Should NEVER Be Auto-Populated:

### 1. Critical Unique Identifiers
-- MUST come from CSV or manual input:
- students.index_no (REQUIRED - no default)
- students.email (REQUIRED - validate format)
- users.username (REQUIRED for login accounts)
- programmes.programme_code (REQUIRED for mapping)

2. Foreign Key References
-- Must resolve from CSV or fail:
- students.programme_id (MUST match existing programme)
- payments.student_id (MUST match existing student)
- users.role_id (MUST match existing role)
- payment_items.due_id (MUST match existing due)

3. Financial Data
-- Require explicit values:
- payments.amount_paid (cannot be 0 or NULL for payment record)
- dues.amount (must be specified for due configuration)


### Import Summary Report:
After import, generate a report showing:
1. Total records processed
2. Successfully imported
3. Failed records (with reasons)
4. Auto-populated fields summary:
    - Default status assignments
    - Generated receipt numbers
    - Estimated admission dates
    - Created user accounts
5. Data quality warnings (missing optional data)
